## 이 문서의 용도

이 문서는 이관 프로젝트를 처음 투입하는 운영자의 실행 순서입니다. 실제 접속 정보는 `.streamlit/secrets.toml`에만 두며, 문서와 Git에는 기록하지 않습니다.

## 최초 투입 순서

1. 실행 PC에 Python, Streamlit, 요구 패키지와 Greenplum·Redshift 접속 드라이버를 준비합니다.
2. `.streamlit/secrets.toml`에 Greenplum, Redshift 연결을 설정합니다. 실제 값은 이 문서에 쓰지 않습니다.
3. DBA가 만든 메타데이터 스키마를 준비합니다. `SrcTgtOrchestrator.py`를 처음 실행하면 초기 설정 화면이 열립니다. 기존 메타가 있으면 먼저 `메타데이터 백업`을 눌러 `테이블명_YYYYMMDD` CTAS 백업을 만들고, 스키마명을 입력한 뒤 `메타 생성`을 누릅니다. 이 작업은 메타 테이블·사용자·이력을 다시 만듭니다.
4. 아래 가상 테스트를 실행합니다. 실패하면 실제 화면을 열거나 실제 DDL을 적용하지 않습니다.
5. 생성이 끝나면 초기 관리자 계정으로 로그인하고 즉시 비밀번호를 바꿉니다.
6. `👤 사용자`에서 운영자 계정을 만들고 그룹·프로젝트·주제영역 범위를 지정합니다.
7. `👤 관리 > 접속`에서 원천·대상 접속을 등록합니다. 접속 ID별로 DBMS, Secrets 섹션명, Airflow 접속 ID만 등록합니다.
8. `🗂️ 주제영역`에서 프로젝트의 상위·실행 주제영역, 이름, 표시 순서와 사용 여부를 입력합니다.
9. `구조조회 > 원천 레이아웃`에서 원천 접속과 스키마를 선택하여 기준일 레이아웃을 적재하고 비교합니다.
10. `🔗 매핑`에서 적재한 원천 레이아웃을 선택하고 대상 접속·테이블·컬럼 설계를 작성합니다.
11. `구조조회 > 대상 반영안`에서 원천 기준일과 대상 매핑을 비교하고 물리설계·DDL을 확인한 뒤 DAG를 생성합니다.
12. Airflow 실행 후 실행 이력, 검증, 산출물, 고객 현황 순서로 확인합니다.

초기 설정이 저장하는 것은 스키마명뿐이며 `.streamlit/migration_setup.toml`에 PC별로 보관됩니다. 이 파일과 실제 연결 비밀값은 Git에 포함하지 않습니다.

기존 메타를 유지하는 환경은 초기화 DDL 대신 `sql/02_mig_connection_migration.sql`을 한 번 적용합니다. 이 파일은 `TB_MIG_CONN`과 기본 접속 참조만 추가하며 기존 매핑·사용자·실행 이력을 삭제하지 않습니다. 스키마명이 `MIG_META`가 아니면 실행 전에 스키마명만 같은 방식으로 치환합니다.

## 사용자 그룹과 권한

| 그룹 | 할 수 있는 일 |
| --- | --- |
| 관리자 | 사용자·권한을 포함한 전체 관리 |
| 팀원 | 주제영역, 매핑, 구조조회, 검증, DAG, 산출물, 실행 이력 |
| 기타 | 조회와 산출물 확인 |

프로젝트 코드는 한 이관 사업의 매핑 묶음, 권한 범위, 산출물·현황 집계 기준입니다. 사용자 권한의 프로젝트 코드가 비어 있으면 전체 프로젝트를, 값이 있으면 그 프로젝트만 허용합니다. 최초 투입 전에 프로젝트 표준 코드 한 개를 정해 주제영역·매핑·권한에 동일하게 사용합니다.

## 원천 수집과 대상 매핑의 경계

접속 ID는 테이블 매핑의 원천·대상 위치를 식별하는 기준값입니다. 실제 비밀번호·호스트·계정은 `secrets.toml` 또는 Airflow Connection에만 두며, 이관 메타에는 저장하지 않습니다. 접속 ID 하나는 Secrets 섹션명과 Airflow 접속 ID 하나를 참조합니다.

원천 구조는 사용자가 다시 입력하지 않습니다. `구조조회 > 원천 레이아웃`에서 선택한 Greenplum 접속의 스키마·테이블·컬럼 순번·타입·PK·NULL·설명을 기준일별로 수집합니다. 레이아웃에는 원천 접속 ID도 함께 저장하므로 동일한 스키마·테이블명이 다른 원천에 있어도 구분합니다. 같은 원천 접속·기준일·선택 스키마를 재적재하면 먼저 삭제되므로 중복되지 않습니다.

기존 원천 레이아웃 이력 테이블에는 최초 조회 시 `SRC_CONN_ID` 컬럼을 추가합니다. 기존 행은 호환을 위해 `SRC_GP`로 조회되므로, 다른 원천으로 수집한 과거 이력은 접속 ID를 확인한 뒤 별도로 보정합니다.

출근 후에는 직전 기준일과 당일 기준일을 비교해 변경 테이블·컬럼을 확인합니다. 대상 반영이 필요하면 `구조조회 > 대상 반영안`에서 같은 기준일의 원천 구조와 대상 컬럼 매핑을 나란히 확인하고, Redshift 분산·정렬·자동 압축과 대상 DDL을 검토·저장합니다. 이 DDL은 DBA 검토용이며 화면에서 실행·승인·배포하지 않습니다.

`🔗 매핑`의 신규 등록은 수집된 원천 레이아웃을 먼저 선택합니다. 원천 스키마·테이블·컬럼은 읽기 전용으로 가져오며, 운영자는 대상 스키마·테이블·대상 컬럼·타입·변환식·적재 방식만 정합니다. 원천 정보와 대상 설계를 한 화면에서 모두 수기로 만드는 방식은 사용하지 않습니다.

## 메타데이터 핵심 구조

| 테이블 | 책임 |
| --- | --- |
| `TB_MIG_SBJ_AREA` | 상위·실행 주제영역 코드, 이름, 표시 순서, 사용 여부 |
| `TB_MIG_SBJ_DAG_MPG` | 실행 주제영역별 DAG ID와 기본·최대 병렬도 |
| `TB_MIG_USR`, `TB_MIG_USR_AUTH` | 로컬 사용자, 비밀번호 해시, 사용자 그룹과 업무 범위 |
| `TB_MIG_CONN` | 원천·대상 접속 ID, DBMS, Secrets 섹션명, Airflow 접속 ID, 사용 여부 |
| `TB_MIG_TBL_MPG` | 원천·대상 테이블 연결, 대상 물리설계, 적재, 버전 |
| `TB_MIG_COL_MPG` | 자동 수집한 원천 컬럼과 대상 컬럼·변환식·검증 여부 |
| `TB_MIG_RUN_LOG` | EXTRACT·LOAD 실행 단계와 처리량·상태 |
| `TB_MIG_ARTF_ITEM` | 산출물 항목명·표시 순서·출력 여부 |

실행 주제영역의 `사용` 여부가 DAG 생성·실행 여부를 함께 제어합니다. DAG 별도 사용 여부는 두지 않습니다. 테이블별 선후행·병렬 그룹·테이블별 병렬 조건처럼 현재 실행기가 해석하지 않는 메타 컬럼은 정리 대상입니다.

## 가상 테스트

실제 DB·비밀값 없이 초기 스키마 검증과 비파괴 DDL 계약, 접속 ID 형식·원천/대상 구분, 초기 비밀번호 변경, 팀원 권한 생성, 원천 접속별 기준일+선택 스키마 레이아웃 교체, 원천 레이아웃에서 대상 매핑으로의 변환, 기존 대상 구조 자동 매핑, 레이아웃 변경 감지, 대상 반영안의 기준일 조회·물리설계 저장·DDL 생성, 접속 참조가 포함된 DAG Python 생성, 가상 EXTRACT·LOAD 성공 흐름을 점검합니다.

```powershell
python 10.Gp2Red\tests\virtual_workflow_test.py -v
python -m py_compile 10.Gp2Red\app\*.py 10.Gp2Red\dag\common\mig_step_runtime.py
```

가상 테스트는 접속·권한·실제 테이블 데이터까지 보증하지 않습니다. 실제 투입은 단일 테이블, 병렬도 1, 별도 작업일자로 시작하고 COUNT·HASH 검증과 실행 이력을 확인한 뒤 범위를 넓힙니다.

초기 설정은 이관 전용 메타 테이블만 삭제·재생성합니다. 대상 업무 테이블이나 스키마 삭제는 수행하지 않습니다.
